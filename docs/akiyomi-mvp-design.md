# アキヨミ（仮）MVP設計書 — 居酒屋の「席が空くまでの時間」自動予測サービス

作成日: 2026-09-01 ／ ステータス: ドラフト v1

## 0. コンセプト

**「今は満席。でもあと20〜35分で4名卓が空く」を、店員の手入力に頼らず自動で見せる。**

- 既存サービスの空白: 「今入れる店」表示（ホットペッパー席押さえ等）や「待ち組数」表示（EPARK等）はあるが、**「空く前」の予測を見せるサービスは国内に存在しない**（2026年9月時点の調査結果）。
- 過去10年の失敗の共通要因は「ピークタイムほど店員が更新できず情報が腐る」こと。本サービスは**時間制（2時間制・飲み放題・コース）と注文イベントからの自動算出**でこの急所を回避する。

## 1. 検証したい仮説（MVPの目的）

MVPは事業を作るためではなく、以下の3仮説を最小コストで検証するために作る。

| # | 仮説 | 検証方法 | 成功基準 |
|---|------|---------|---------|
| H1 供給 | 時間制・注文データから席の空き時刻を±10分程度で予測できる | 実店舗で予測値と実際の空き時刻を記録 | 30分前時点の予測が±10分以内: コース卓80%以上、全卓60%以上 |
| H2 需要 | 「あと◯分で空く」表示・通知が来店行動につながる | 客側UIの利用ログ＋店頭ヒアリング | 通知登録→来店の転換が計測でき、「表示を見て行ったら入れなかった」率5%未満 |
| H3 経済 | 店がこの仕組みにお金を払う | 8週間運用後の店舗ヒアリング | 参加店の7割が「継続したい」、月額3,000〜5,000円 or 送客100〜300円/人に支払意思 |

**H1が崩れたら他は無意味なので、H1を最初に単独で検証する（Phase 0）。**

## 2. スコープ

### やること
- 1エリア（例: 新橋・赤羽など、時間制・宴会業態が密集する繁華街を1つ選定）× 10〜20店
- 卓単位の状態管理と「n名が入れる最早時刻」の区間予測
- 客側: スマホWebアプリ（地図＋リスト＋LINE通知）
- 店側: タブレット/スマホで使える最小限の卓ボード（着席時1タップのみ）

### やらないこと（意図的に捨てる）
- 予約機能・決済（既存グルメサイトと戦わない。「見える化＋通知」だけ）
- 機械学習（v0はルールベース＋統計。データが貯まるまでMLは作らない）
- センサー・カメラ（コストと設置負荷で過去のサービスが全滅した道）
- 全国展開・多エリア（密度の壁を避けるため1エリア集中）
- ネイティブアプリ（Web＋LINEで十分）

## 3. プロダクト構成

```
[店側] 卓ボード(Web)  ──着席1タップ/会計1タップ──▶ Firestore
[将来] スマレジAPI Webhook ──注文/会計イベント──▶ (Phase 2で置き換え)
                                    │
                          [予測エンジン v0]
                       Cloud Functions (ルールベース)
                                    │
[客側] 地図+リスト(Web) ◀── 「n名卓が空く予測時刻の区間」
        └─ LINE通知「◯◯で4名卓があと15分で空きそうです」
```

技術スタックは tetsu-log と同じ構成を流用する: **単一HTML + Firebase（Firestore / Hosting / Cloud Functions）+ LINE Messaging API**。開発者1人で2〜4週間で構築可能な範囲に収める。

### 3.1 店側: 卓ボード（属人性を「着席時の1タップ」まで削る）

店員の操作は卓のライフサイクルで最大2回だけ:

1. **着席時**: 卓を選んで「人数」と「プラン」をタップ（フリー / 90分制 / 2時間制 / コース）。多くの店で案内時に頭の中でやっている判断をそのまま画面に置くだけ。5秒で終わるUI。
2. **会計時**: 「会計」ボタン（Phase 2でPOS連携により自動化。これが本命の属人性ゼロ化）。

退店・片付け完了は入力させない（バッシング時間は固定オフセット＋実績学習で吸収する）。

### 3.2 予測エンジン v0（ルールベース）

卓の状態機械: `vacant → seated → (last_order) → paying → bussing → vacant`

**コース・時間制卓（予測の主力。宴会シーズンの居酒屋では多数派）:**
```
空き予測時刻 = 着席時刻 + 制限時間 + 延長補正 + バッシング時間
```
- 制限時間: 着席時に選んだプラン（90分/120分）
- 延長補正: 店ごとの延長発生率 × 平均延長時間（初期値0、実績から更新）
- バッシング時間: 初期値10分（実績から店ごとに更新）

**フリー卓（分散が大きい。区間で出す):**
- 業態別の滞在時間分布（初期値: 2名110分、3名以上150分など。運用実績で店別に置換）から「経過時間を条件とした残り時間」のp50とp80を算出
- シグナルによる上書き（Phase 2でPOSから自動取得、Phase 1では会計タップのみ）:
  - 会計タップ → 残り = バッシング時間のみ
  - LO時刻通過（時間制卓） → 残り ≤ 制限時間までの残分
  - （Phase 2）締め・デザート注文 → 残り ≤ 25分、注文間隔の減衰 → 残り時間短縮

**出力仕様（信頼性を守る設計。ここが生命線):**
- 表示は必ず**区間**（例:「20〜35分後」）。下限=p50、上限=p80
- 客側の並び順・通知は**悲観側（p80）**を基準にする。「早く空いた」は許され、「まだ空いてない」は一発で信頼を失うため
- 予測が外れた場合（p80超過）: 対象店で使えるドリンククーポンを自動発行（店側と原価負担を事前合意）
- データ不足・確度が低い卓は「予測なし（満席）」表示に落とす。無理に出さない

### 3.3 客側: 空き待ちマップ

- 「今から◯名で飲みたい」を入力 → 周辺の参加店を3分類で表示:
  1. **今入れる**（空席あり）
  2. **もうすぐ空く**（「4名卓: 20〜35分後」区間表示）
  3. 満席（予測なし）
- 「空いたら通知」ボタン → LINEで「あと15分で空きそう」「空きました（15分間キープ可※店と合意した場合のみ）」
- アカウント登録なし・LINEログインのみ。摩擦を最小化

## 4. データモデル（Firestore）

```
stores/{storeId}
  name, geo, genre, seats_total,
  settings: { bussing_min: 10, lo_offset_min: 30, extension_rate: 0.0 }

stores/{storeId}/tables/{tableId}
  capacity, status: vacant|seated|paying|bussing,
  seated_at, party_size, plan: free|limit90|limit120|course,
  predicted_vacant_at: { p50, p80 }   // エンジンが書き込む

stores/{storeId}/events/{eventId}     // 学習・精度検証用の生ログ（最重要資産）
  table_id, type: seated|checkout|vacated|prediction_snapshot, at, payload

watch_requests/{id}                    // 客の「空いたら通知」
  line_user_id, store_id, party_size, created_at, notified_at, visited(手動追記)
```

`events` が精度検証（H1）とモデル改善の元データになる。**予測スナップショット（30分前・15分前時点の予測値）を必ず残す**こと。後から答え合わせできない設計にしないのが鉄則。

## 5. 段階的計画

### Phase 0: 予測精度の単独検証（2〜3週間、1〜2店舗）
- 客側UIは作らない。卓ボード＋予測エンジン＋ログだけ
- 協力店1〜2店（知り合いの店が理想）で営業中に運用し、予測 vs 実際の空き時刻を記録
- **ゲート: コース卓±10分ヒット率80%、全卓60%を下回ったら、ロジック改善かピボット（時間制卓限定サービス化など）を判断。客側を作るのはこの後**

### Phase 1: 1エリアでの需要検証（6〜8週間、10〜20店舗）
- 客側Web＋LINE通知を公開。エリアの金曜夜に集中させる（ポスター/店頭QR/SNS）
- 営業: エリアの時間制・宴会業態を足で回る。無料＋クーポン原価負担ゼロを条件に参加を集める
- H2・H3の計測とヒアリング

### Phase 2: 属人性ゼロ化（Phase 1成功後）
- スマレジ・プラットフォームAPI（国内で実質唯一のオープンPOS API）とWebhook連携し、会計イベント・注文イベントを自動取得 → 店側タップを撤廃
- 締め注文・注文間隔減衰シグナルを予測に組み込み、フリー卓の精度を引き上げ
- ここで初めて「店員が何もしなくても空き予測が出る」という本来のコンセプトが完成する

## 6. KPI（週次で追う数字）

| 分類 | 指標 | 目標 |
|------|------|------|
| 精度 | 30分前予測の±10分ヒット率（コース卓/全卓） | 80% / 60% |
| 精度 | 「空き表示→行ったら満席」報告率 | < 5% |
| 需要 | 週間ユニーク閲覧者（エリア内） | 300人（8週目） |
| 需要 | 空き通知登録数/週、通知→来店transition | 計測できること自体が目標 |
| 供給 | 参加店の卓ボード入力率（着席タップ実施率） | > 90% |
| 経済 | 8週後「継続したい」店舗比率 | ≥ 70% |

## 7. 主要リスクと対策

| リスク | 対策 |
|--------|------|
| 予測が外れて信頼崩壊 | 区間＋悲観側表示、確度低は非表示、外れクーポン補償（設計に組込済） |
| 店員が着席タップをサボる | 入力率をKPI化し週次で店にフィードバック。Phase 2のPOS連携で根本解決 |
| 密度不足で客に価値が出ない | 1エリア集中＋金曜夜集中。面ではなく「この街のこの夜」で成立させる |
| リクルート/LINEヤフーが同機能を出す | MVPは「エリア独占の実運用データ」と「予測精度ノウハウ」の先行蓄積を優先。速度勝負と割り切る |
| 店側の「空席表示=不人気の告白」心理 | 「満席です・でももうすぐ空きます」という**強気の見せ方**を初期設定にする（空いている店ほど目立つ従来型と逆） |

## 8. コスト概算（Phase 0〜1）

- 開発: 1人 × 6〜10週（本人開発想定なら人件費ゼロ）
- インフラ: Firebase無料枠内〜数千円/月、LINE Messaging API無料枠
- クーポン補償原価: 上限を設定（例: 月2万円）して実績を見る
- 店舗開拓: 交通費・営業ツール程度

**現金支出は月数万円以内に収まる。最大の投資は開発時間と店舗開拓の足。**
